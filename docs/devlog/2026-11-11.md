## 0. 结论先行（业务影响）

项目当前最大的风险不是棋力，而是**决策依据错了**。

`docs/v8-factored-head.md:145` 建议「放弃纯 CNN 路线、转 Transformer」，`docs/chess-strength-roadmap.md:22` 把「重训 NN（2-3 天 GPU）」列为第一优先级。这两个决策建立在「NN 比随机还差、问题不在搜索」的诊断上。本次审查用实测推翻该诊断：

| 文档诊断 | 实测结论 |
|---|---|
| NN val_acc 5%，比随机 12.5% 还差 | 口径是 **8100 类 masked Top-1**，随机基线 ≈ 1/40 = **2.5%**。5% 是随机的 **2 倍**，不是「比随机差」。`12.5% = 1/8` 在全仓库无任何代码来源 |
| 「是 NN 模型本身的问题，不是搜索的瓶颈」 | MCTS 有 **3 个确认缺陷**：终局价值符号反了、非根节点 PUCT 探索项恒为 0、每 sim 分配 1.93 MB |
| 「NN 推理是 MCTS 最大瓶颈」 | 实测 NN 推理 1.609 ms/sim，总 3.18 ms/sim → **NN 只占 50%**，另一半是搜索侧开销 |
| 「Top-10 卡 34% → 堆数据无收益 → 架构瓶颈」 | 产出该指标的脚本 `legal_mask` 不随翻转重映射，**acc/Top-K 至少腰斩**，归因失效 |

**建议：先修搜索侧 3 个缺陷 + 度量层 mask bug，再重跑一次评测，然后才决定是否换架构。** 在此之前不要把「放弃 CNN」当已证结论。

### A. 确认缺陷 — 搜索与规则（最高优先级）

**A1【严重】MCTS 把被将杀的一方评为赢家（符号反了）**
`ChineseChess.Core/Services/MctsAiService.cs:93-100`
```csharp
if (status == GameStatus.RedWins)
    value = node.Side == Side.Red ? -1f : 1f;  // 注释写 "current mover lost"
```
`GetGameStatus` 语义（`XiangqiEngine.cs:153`）：`RedWins ⟺ turn==Black 且无合法着`。故此时 `node.Side==Black`，表达式取 `+1f`，而黑方是**输家**，应为 `-1f`。`BlackWins` 分支同理反。
**实测**（`evidence/probe1_sign.txt`）：构造黑方被将杀局面 → `GetGameStatus=RedWins`、黑方合法着 0、被将军 True，MCTS 表达式给出 `+1`，正确值 `-1` → **SIGN INVERTED**。
影响：MCTS 主动寻求被将杀。这是 20-0 横扫的最可能主因。

**A2【严重】非根节点 `VisitCount` 永不自增 → PUCT 探索项恒为 0**
`MctsAiService.cs:126` 只有 `root.VisitCount++`；回溯（`:119-125`）只更新 `parent.ChildN/ChildW`。而 `SelectChild:193` 对**任意**节点读 `node.VisitCount`：
```csharp
var sqrtN = MathF.Sqrt(node.VisitCount);   // 非根节点恒为 0
var u = CPuct * p * sqrtN / (1 + n);       // => u == 0
```
全文件 `VisitCount` 仅 4 处引用（`:126/:193/:329/:353`），无其他自增点。
影响：根以下退化为纯贪心 argmax Q，PUCT 名存实亡；`CPuct=1.5` 与 Dirichlet 噪声只在根生效。

**A3【严重】MCTS 每次模拟分配 ~1.93 MB**
`MctsAiService.cs:171-175` 按 `MoveEncoder.ActionCount=8100` 开 5 个稠密数组，而实际合法着仅 ~45。
**实测**（`probe4_mcts.txt` / `probe6_alloc.txt`）：

| 项 | 实测 |
|---|---|
| 5 个 8100 数组 | **221.6 KB/op** |
| 5 个 45 数组 | **1.4 KB/op**（158× 缩减） |
| `GetLegalMoves(board,side,history)` | **795.6 KB/op，574.9 µs/op** |
| `GetGameStatus(board,side,history)` | **801.4 KB/op，553.7 µs/op** |
| MCTS 整体 | 400 sims → **769.5 MB**，**1970 KB/sim**，3.18 ms/sim |
| 纯 NN 推理 | **1.609 ms/call** |

归因吻合：801 + 796 + 222 ≈ 1819 KB ≈ 实测 1970 KB/sim。
影响：按文档 3000 sims 目标，每步约 **5.8 GB** 分配量。GC 压力是 sims 上不去的另一半原因。

**A4【高】经典搜索每节点重复生成走法两次**
`XiangqiAiService.cs:237` 调 `GetGameStatus(board,turn)`（内部 `XiangqiEngine.cs:146` 调 `GetLegalMoves`，结果只取 Count 后丢弃），`:245` 又调一次 `GetLegalMoves`。
实测 `GetGameStatus`(256.6 µs) ≈ `GetLegalMoves`(263.4 µs) → 最贵操作白做一遍。

**A5【高】history 感知走法生成：代价与收益严重失衡**
`XiangqiEngine.cs:204-224 GetPositionHistory` 每次调用把整段历史逐步 Undo（每步 CloneBoard），再对每个局面用 `GetPositionKey`（`:226-238`，90 个 `piece.Id` 字符串 Join）建 key。
实测：带 history 比不带贵 **+300 µs / +800 KB** 每次调用；而在 **1043 个随机对局局面中，history 过滤删掉的着法数 = 0**（`probe5_repetition.txt`）。
注：随机对局极少产生长将序列，故「0 删除」不能外推为「永远无用」；但当前实现把 O(H) 字符串重建放在每个搜索节点上，是搜索浅的主因。
实测整体：**7556 nodes/sec**（Level 4，2007 ms，depth 4，15168 节点，`probe3_nps.txt`）。文档把慢归因于「ApplyMove 全是对象分配」，但实测 `ApplyMove` 仅 **0.2 µs**、`CloneBoard` **0.1 µs** —— 归因错误。

**A6【中】重复局面 key 用 `piece.Id` 而非 (side,type)**
`XiangqiEngine.cs:233` `parts.Add(board[row,col]?.Id ?? ".")`，Id 形如 `red-rook-0`。同方同种棋子互换位置会产生不同 key，而它们在重复局面判定上等价 → 漏判。

**A7【中】QSearch 被将军时仍 stand-pat**
`XiangqiAiService.cs:326-329`：先算 `standPat` 并 `if (standPat >= beta) return beta;`，无 `IsInCheck` 守卫。被将军时「不走」不是合法下界。`:329` `qDepth>=8` 直接返回 alpha 同样可能在被将军时返回虚高值。Elo 影响未测。

**A8【中】根节点 α-β 截断分数被当精确分用于采样**
`XiangqiAiService.cs:114-144`：根节点 alpha 随首个着法上升，后续着法以 `(-beta,-alpha)` 搜索，fail-low 返回的是**上界**而非精确分。`SelectMove:158-172` 却把这些分数直接排序、按 `NearBestWindow` 取候选。
影响：后搜的着法分数被系统性压低 → 采样池比预期窄，偏向 TT/MVV-LVA 靠前的着法。直接削弱 README:13「从近似最优候选中采样，避免反复走同一盘」的目标。

**A9【中】士象「正确位置」集合错误（改动 D 新代码）**
`XiangqiAiService.cs:704-710 IsElephantSlot`：要求 `col∈{2,6}`、红方 `row∈{9,7,5}`。但象走田字，红方象可达列为 {0,2,4,6,8}，**(7,2)/(7,6) 根本不可达**，而真正的中枢象位 **(7,4) 被排除**。
`:697-702 IsAdvisorSlot`：红方 `row∈{7,9}`、`col∈{3,5}`，漏掉中枢仕位 **(8,4)**；注释写的 `(3,3),(3,5),(5,3),(5,5)` 是黑方九宫行号，与代码不符。
影响：king-safety「站位正确 +6」奖励发给了不可达格、漏掉了关键防守格。

**A10【低】马的 mobility 把落在己方子上的格子算进去**
`XiangqiAiService.cs:647-651`：只查马腿与边界，未查落点占用；注释「horse always lands on empty or enemy square」为假。

### B. 确认缺陷 — 校验/度量工具（「假通过」）

**B1【高】`Core.Verification` 恒通过，等于没有护栏**
`ChineseChess.Core.Verification/Program.cs:43` 只回溯 4 层：`bin/Debug/net8.0` → `ChineseChess/artifacts`（实际在仓库根 `artifacts/`，需 5 层）；`:46` 回退到 BaseDirectory，而该 csproj 未复制模型 → `:48-53` 打印 Skipping 并 return。`:86-89` catch 吞异常，进程退出码 0；`:84` 打印「✅ passed」但全程无断言。

**B2【高】`verify_onnx.py` / `diagnose_nn.py` 对当前部署模型必然失败，且从不校验数值**
实测部署模型输入为 `board_input[batch,16,10,9]`（见 D1），而 `verify_onnx.py:22`、`diagnose_nn.py:37` 硬造 `(1,14,10,9)` → ORT shape 报错。两者还硬编码不存在的 `data/selfplay/train_500.jsonl`（`verify_onnx.py:17`、`diagnose_nn.py:67`）。`verify_onnx.py` 全程无 PyTorch↔ONNX 对比、无容差断言，`:120` 无条件打印「✅ verified」。

**B3【高】`train_v7_combined.py` 的 `legal_mask` 不随翻转重映射**
`:118-131` 定义了 `_remap_legal_moves`，**全文件零调用**；`:277` `features.flip(-1)`、`:278-284` 重映射了 move，但 `:287` `legal_mask[legal]=True` 用的仍是翻转前的 legal 集合。

注意：`:378` 的 CE loss 用**未 mask** 的 logits，故**梯度不受影响** —— 这是纯测量口径缺陷，不是模型质量缺陷。

**B7【中】`train_v7_combined.py:312` chunk 缓存无输入指纹**
仅以 `meta.pt` 是否存在判断 → 换 `--input` 但沿用默认 `--chunk-dir` 时，训练的是上一份数据，静默。

**B8【中】`run_parallel_selfplay.sh:7-9` 硬编码 `/e/Projects/WorkBuddy/...`**（仓库现在 D 盘）；`set -e`(`:5`) 下 `wait $PID`(`:62`) 非零即退出，`:64-69` 失败计数与 `:98` 合并分支不可达。

### D. 风险（机制存在，当前无实测证据）

- **D1** Negamax 可能返回 `double.NegativeInfinity`：`XiangqiAiService.cs:237` 的终局判定用 `GetGameStatus(board,turn)`（**不传 history**），而 `:245` 用带 history 的 `GetLegalMoves`。若后者为 0 而前者非终局，`best` 保持 -inf 并在 `:308` 返回，父节点得到 +inf。**探针在 1043 个随机局面中复现 0 次**，触发需长将序列 → 降级为风险。
- **D2** TT cutoff（`:217-234`）在终局判定（`:237`）之前，且 hash 不含 history → 可能用旧分数覆盖实际终局。文档 `classic-ai-improvements.md:114` 已登记为已知局限。
- **D3** TT 满 250k 时**全表清空**（`:412`）而非淘汰 → 周期性丢失全部复用。实测 TT 命中率 3.51%，其中 64%（341/533）可用于截断，说明「命中即有效」，问题在命中率。
- **D4** 资源释放：`ShellViewModel.cs:24-25` 的 `_neuralAi/_mctsAi` 实现 IDisposable 却从不释放；`:274-279` 只置 null 不 Dispose CTS；`SoundService.cs:24` `Task.Delay(180).ContinueWith(...)` 异常无人观察，SoundPlayer 未 Dispose；`Bootstrapper.cs:39 async void OnStartup` 无 try/catch。
- **D5** 无边框窗口：`ShellView.xaml:12-14` `WindowStyle=None`+`AllowsTransparency=True`+`ResizeMode=CanResize`，无 WindowChrome/MaxHeight 修正 → 最大化可能盖任务栏（需运行确认）。
- **D6** 训练可复现性：`train_v7_full_policy.py`/`train_v7_continue.py`/`train_v7_combined.py` **完全无 seed**；v7/v8 全部硬编码 CPU；**六份脚本无一保存 optimizer/scheduler state** → 续训丢 AdamW 动量与 cosine 进度；`train_v7_full_policy.py:257`、`train_v7_continue.py:229`、`train_cnn_policy_value.py:386` 的 **val 集仍走 p=0.5 随机翻转**（v8:323 已修）→ 指标逐 epoch 抖动、best 选择带噪。
- **D7** 训练/验证划分：v8:314-316、cnn:293-297、MLP:117 按 **sample shuffle** → 同局相邻局面泄漏；v7_full:251-253 / v7_continue:223-225 按文件顺序切（局级无泄漏）；combined:326-327 取末 chunk（无泄漏但 val 只来自最后一个并行进程）。
- **D8** NN 输入无历史/重复平面（14+2）→ 无法感知三次重复与长将禁着，而 C# `GetLegalMoves` 用 history。与文档「和棋均为重复局面」吻合。
- **D9** `train_v8_factored.py:131` 不校验 `SideToMove∈{1,-1}`（其余脚本校验）→ 若喂 0/1 枚举数据，`:88 result*side_to_move` 恒 0 且侧别平面反。

### E. 产品选择（不是 bug，未列为必须修）

- Level 1 确定性返回 `legalMoves[0]`（`XiangqiAiService.cs:63-66`）。
- 长将只「禁着」不「判负」，且无长捉规则；`GameStatus` 无长将判负项。

### 2.4 本次修复过程中我自己引入并被抓出的回归（重要留痕）

**A8 全窗口参数符号写反**：第一版把子节点的 **beta** 设成 `double.NegativeInfinity`（应为 `PositiveInfinity`）。
后果链：qsearch 的 `if (standPat >= beta) return beta;` 在 beta=-inf 时恒真 → 返回 -inf → 父节点取负得 **+inf** → `SearchStats.BestScore` 为无穷 → SelfPlay 序列化抛 `ArgumentException: .NET number values such as positive and negative infinity cannot be written as valid JSON`，**自博弈数据生成直接崩溃**。

- **怎么发现的**：不是单测，是 **SelfPlay 冒烟测试**。我第一版 `MoveSamplingTests` 只断言「走法合法」，对分数被污染完全不敏感——非法分数照样能选出合法着法。
- **修复**：`sampling ? double.PositiveInfinity : -alpha`（`XiangqiAiService.cs:121`）。
- **补护栏**：`SampledMovesAreAlwaysLegal` 增加 `double.IsFinite(BestScore)` 断言；新增 `SamplingScoresAreFiniteAtEveryLevel` 覆盖 level 1-4。revert-run 确认两条均 RED，修复后 GREEN。
- **教训**：纯性能/口径类修复也要有**数值健全性断言**（有限性、值域），只断言「输出形状正确」抓不到口径污染。跨进程冒烟测试（真跑 SelfPlay 写 JSONL）比单测更早暴露了它。

**陈旧二进制假故障**：修好后重跑仍崩溃，原因是 `dotnet run --no-build` 用的是 revert-run 期间构建的 SelfPlay。显式 `dotnet build` 后正常。
- **教训**：revert-run 验证法之后必须**显式重建**再跑集成验证，否则会把陈旧产物当成未修好。

## 3. 过程中被测试纠正的 4 个自身错误（留痕）

TDD 的价值在本次很具体——**4 次是测试写错/fixture 写错，不是产品错**：

1. **A1 fixture 第一版不合法**：红车 (1,0) 挡住了 (5,0)→(0,0)，那步棋根本不在合法着列表里。已加 `Assert.Contains(GetLegalMoves(...))` 合法性前置断言防止再犯。
2. **A1 fixture 第二版不适合**：红方多两车 → NN value 饱和到 0.9925，PUCT 探索项 `1.5·p·√N` 压不过饱和 Q，导致 **mate 着法 400 sims 内 N=0 从未被访问**。换成子力接近均势（红~3500 vs 黑~3080）的局面后，一步杀才凸显。
3. **长将护栏断言反了**：引擎在**第 2 次**出现被将军局面时就禁着（不是第 3 次），所以那步棋在 m5 之前已被禁。引擎是对的，测试预期错了。
4. **stalemate fixture 不合法**：黑将放在 (0,0)，不在九宫内。改为 (0,4) + 红马 (2,4) 控 (0,3)/(0,5) + 红车 (1,8) 控 (1,4) 的真·无子可动局面。
5. **可复现契约理解错**：`_seededRandoms` 按 seed 缓存 `Random` 实例并跨调用推进，故「同实例同 seed 两次调用结果相同」不成立；正确契约是「新实例 + 同 seed」。
6. **分配测试在解决方案级并行下假失败**：`GC.GetTotalAllocatedBytes` 是**进程级**计数器，被并行测试集合污染。已加 `[assembly: CollectionBehavior(DisableTestParallelization = true)]`。
